Shigaflow v21 — Google Drive ZIP capture + duplicate Chrome Save As

ROOT CAUSE (Google Drive multi-file / folder ZIP)
The service worker looked up the Drive download by item.tabId. Chrome's chrome.downloads
DownloadItem has no tabId field, so the check always failed and the ZIP capture exited
immediately, for every earlier version of the ZIP fix. Chrome then downloaded the ZIP itself.

WHY "The file type '' is not in your allowed extensions list"
When the Drive selection was not recognised as several files, Shigaflow tried to fetch it by file id.
For a folder (or any non-file id) Drive answers with a web page. The app's probe hid that, the name
ended up with no extension, and the empty-extension message appeared.

CHANGES (BrowserExtension 1.4.0 — reload it in chrome://extensions and restart the browser)
- Drive's Download command is no longer blocked or guessed from the page. The content script only
  tells the service worker to expect a Drive download. Drive then makes Chrome start the real
  download (one file, several files zipped, or a folder zipped) and the service worker captures
  it, sends it to Shigaflow with the Google cookies, and cancels Chrome's copy.
- The marker is global (no tabId) and valid for 5 minutes, so slow "preparing ZIP" waits still work.
- The old selection/file-id guessing code was removed.

CHANGES (duplicate Chrome Save As dialog)
- The service worker remembers links it has handed to Shigaflow. If Chrome ALSO starts a download
  of the same link, Chrome's copy is cancelled and removed from its download list once Shigaflow
  has acknowledged the handoff, so Chrome's Save As dialog does not appear.
- If the handoff to Shigaflow fails, Chrome's download is left alone.

CHANGES (app)
- A link that returns a web page instead of a file now shows "The server returned a web page
  instead of a file" instead of the misleading empty file-type message.

Files changed: BrowserExtension/service_worker.js, capture_links.js, manifest.json,
               Shigaflow/DownloadService.cs, Shigaflow/MainWindow.xaml.cs
The native host is unchanged. Not tested against live Chrome/Drive/Windows here.
