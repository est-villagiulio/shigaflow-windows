Shigaflow Windows torrent engine migration
===========================================

- Replaced the MonoTorrent 3.0.2 package and all MonoTorrent source references
  with LibtorrentSharp 0.1.0-alpha (libtorrent-rasterbar native engine).
- Target is Windows x64 / .NET 8. The NuGet package supplies lts.dll under
  runtimes/win-x64/native; the existing publish script already publishes win-x64
  and extracts native libraries from the single-file executable.
- Magnet adds use LibtorrentSession.Add(AddTorrentParams.MagnetUri). The
  LibtorrentSharp binding returns magnets paused, so the adapter explicitly calls
  MagnetHandle.Resume() to start DHT/tracker/peer metadata exchange.
- .torrent adds use TorrentInfo + AddTorrentParams.TorrentInfo and start the
  returned TorrentHandle.
- Existing WPF list now reads libtorrent TorrentStatus (state, progress, byte
  rates, downloaded bytes, peer count, total size) rather than MonoTorrent Monitor.
- Pause/resume/stop/remove are adapted for both handle types. Magnet stop maps to
  pause because the binding's MagnetHandle has pause/resume but no separate stop.
  Removing a torrent detaches it from the session without deleting downloaded files.
- DHT/LSD/PEX/uTP are provided by libtorrent-rasterbar session defaults. A dynamic
  TCP listen port is selected to avoid a fixed-port collision preventing startup.
- Sidebar text remains centered: “Shigaflow” / “weebs at it finest!”.

Important validation status
---------------------------
This environment does not have the .NET SDK and cannot build or run the Windows
application. The source migration is implemented against the published LibtorrentSharp
0.1.0-alpha API, but a Windows x64 restore/build and runtime test are still required.
The package is alpha, so the first Windows build is also an API/package compatibility
check. Test magnet metadata retrieval, .torrent adds, pause/resume, stop, remove,
restart/restore, and seeding before using it as a production build.
